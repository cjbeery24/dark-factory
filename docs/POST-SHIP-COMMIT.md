# What to Commit After a Successful SHIP

After `dark-factory run` outputs `SHIPPED: <spec-name>`, commit the
implementation and selected pipeline artifacts to the target project repo.

## Commit (implementation)

| Path | What | Why |
|------|------|-----|
| `SOURCE_DIRS` (e.g. `apps/api/src/`) | Implementation code | The shipped product |
| Test directories (e.g. `__tests__/`, `integration/`) | Self-tests written by implementer | Part of the shipped code |
| `package.json`, `Cargo.toml`, etc. | Dependency changes | Implementation may add deps |
| Lint/build config (e.g. `eslint.config.js`, `tsconfig.json`) | Config changes | Implementation may modify tooling config |

## Commit (pipeline artifacts)

| Path | What | Why |
|------|------|-----|
| `.dark-factory/architecture/` | Manifest, `environment.toml`, deltas, hints | **Living contract.** Future architects read `environment.toml` to understand existing tooling. Future specs emit deltas that amend it. The manifest records architectural decisions that led to SHIP. |
| `.dark-factory/shipped-scenarios/<spec>/` | Blind scenarios + `.registry-meta` | **Regression baseline.** These are the AC-aligned tests the shipped code was validated against. Powers team-wide regression testing. |
| `.dark-factory/shipped-scenarios/<spec>/review.md` | Code review | **Quality provenance.** The review that justified the SHIP decision. |
| `.dark-factory/shipped-scenarios/<spec>/defect-registry.md` | Known gaps | **Gap contract.** Documents defects accepted when shipping with gaps. Tells future developers "we know this is broken." |
| `.dark-factory/plan/shipped.jsonl` | Ship ledger | Records which specs shipped, when, and the env hash at ship time. |
| `.dark-factory/config.toml` | Pipeline config | Project-level pipeline settings. |
| `.dark-factory/reviews/<spec>-validation.md` | Spec validation result | Documents that the spec passed completeness checks before entering the pipeline. |
| `.dark-factory/reviews/<spec>-validation.status` | Validation status | Machine-readable validation outcome. |
| `.dark-factory/specs/` | Specifications | Already tracked — no action needed on ship. |
| `.dark-factory/plans/` | Project plans | Already tracked — no action needed on ship. |

## Do NOT commit

| Path | What | Why skip |
|------|------|---------|
| `.dark-factory/reports/*` | Gate reports, telemetry, counts, defects JSON, test results | Ephemeral per-run output. Regenerated every run. `defect-registry.md` is the exception — copied to `shipped-scenarios/` on ship. |
| `.dark-factory/audit/*` | Per-run audit logs, gate telemetry | Debugging artifacts. Ephemeral. |
| `.dark-factory/state/*` | Pipeline state files, anchor manifests | Ephemeral. Tracks in-progress run state. |
| `.dark-factory/scenarios/` | Live blind scenarios | Regenerated per run. `shipped-scenarios/` has the archived copy. |
| `.dark-factory/reviews/*-feedback-iter*.md` | Oracle-to-implementer feedback | Ephemeral. Only useful during the iteration loop. |
| `.dark-factory/reviews/*-oracle-output-iter*.md` | Raw Oracle JSON output | Debugging artifact. |
| `.dark-factory/reviews/*-escalation.md` | Escalation reports | From failed runs. Stale after a successful SHIP. |
| `.dark-factory/holdouts/` | Adversarial QA scenarios | Written blind without seeing source. Not validated against shipped code. May serve as a future regression suite but not proven. |
| `.dark-factory/precheck/` | Advisory pre-check findings | Stale after implementation. Derivable by rerunning. |
| `.dark-factory/agents/`, `.dark-factory/templates/` | Framework files | Managed by `dark-factory init --update`. Not project customizations. |
| `metrics.jsonl`, `events.jsonl` | Pipeline metrics/events | Runtime telemetry. |
| Build caches (`tsconfig.tsbuildinfo`, etc.) | Build artifacts | Regenerated on build. |

## .gitignore

The `.dark-factory/.gitignore` generated by `dark-factory init` should
already exclude most ephemeral artifacts. After reviewing your project's
gitignore, ensure it covers:

```gitignore
# Ephemeral per-run
scenarios/
audit/*
state/*
reports/*
metrics.jsonl
events.jsonl
events.jsonl.lock
worktrees/

# Ephemeral reviews (keep validation files)
reviews/*-feedback-iter*.md
reviews/*-oracle-output-iter*.md
reviews/*-escalation.md

# Not validated against shipped code
holdouts/
precheck/

# Framework files
agents/
templates/
```

## Pipeline automation

On SHIP, the pipeline automatically copies `review.md` and
`defect-registry.md` into `shipped-scenarios/<spec>/`. The
`dark-factory init` gitignore template excludes ephemeral artifacts
and tracks `shipped-scenarios/` by default.

## After commit — append a calibration row

Before closing out a SHIP run, append one row to the dark-factory
calibration dataset (`docs/post-mortem-dataset.jsonl` in the
dark-factory repo). For SHIP outcomes the row is short — outcome,
iteration count, validator metrics, no root-cause codes:

```bash
dark-factory post-mortem append \
  --spec <spec-id> --run-id <pipeline-run-id> --date YYYY-MM-DD \
  --target-project <name> --outcome shipped --iterations <N> \
  --validator-verdict {PASS|FAIL} --validator-score <0-100>
```

Calibration data lives with the framework (cross-project), not in
the target project. See E2 in
`docs/plans/2026-04-14-spec-reliability-and-pipeline-hardening.md`.
