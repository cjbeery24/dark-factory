# Team Setup Guide

## Overview

This guide helps a small team (2-5 developers) adopt the Dark Factory workflow. It covers roles, conventions, onboarding, and coordination.

---

## Team Roles

In a small team, people wear multiple hats. Here's how to divide Dark Factory responsibilities:

### Spec Owner (1 per feature)
- Writes the initial specification
- Responsible for spec quality and completeness
- Addresses Spec Validator feedback
- Final authority on "what" the feature should do

### Pipeline Operator (any team member)
- Runs the Dark Factory pipeline (Steps 2-7)
- Ensures Docker images are built and up to date
- Reports results back to the Spec Owner

### Human Oracle (rotating)
- Reviews escalated NO-SHIP decisions (iteration 3 failures)
- Makes final call on edge cases the AI Oracle can't resolve
- Provides feedback to improve specs and agent definitions

**Recommended rotation:** Each team member takes one week as the Human Oracle.

## Onboarding a New Team Member

### Day 1: Understand the Framework
1. Read `AGENT.md` — understand the pipeline architecture
2. Read `docs/WORKFLOW.md` — understand the operational steps
3. Read `docs/SPECIFICATION-GUIDE.md` — understand how to write specs

### Day 2: Write a Practice Spec
1. Pick a small feature or bug fix
2. Write a spec using the appropriate template
3. Run it through the Spec Validator
4. Iterate until it passes validation

### Day 3: Run the Pipeline
1. Build Docker images: `bash docker/build-images.sh <language>`
2. Take the validated spec from Day 2
3. Run the full Dark Factory pipeline end-to-end
4. Observe how Docker containers enforce information barriers
5. Review the outputs at each stage

### Day 4: Review and Calibrate
1. Review someone else's spec
2. Manually review an AI-generated implementation
3. Compare your judgment with the Reviewer agent's assessment
4. Discuss discrepancies with the team

## Team Conventions

### Spec Naming
```
.dark-factory/specs/[YYYY-MM-DD]-[feature-name].md
```
Example: `.dark-factory/specs/2025-06-15-user-auth-retry.md`

### Branch Strategy
```
feature/df-[spec-name]     # Feature branches
fix/df-[spec-name]         # Bug fix branches
refactor/df-[spec-name]    # Refactoring branches
```

### Commit Messages
```
[dark-factory] feat: implement user auth retry (spec: 2025-06-15-user-auth-retry)
[dark-factory] test: add blind scenarios for user auth retry
[dark-factory] fix: address iteration 2 feedback for user auth retry
```

### PR Description Template
```markdown
## Spec
[Link to spec file]

## Dark Factory Report
- Iterations: X
- Blind scenario results: X/Y passed
- Review score: X/100
- Oracle decision: SHIP

## Changes
[Auto-generated by implementer's notes]

## Spec Compliance
[Paste from Oracle's release summary]
```

## Shared Configuration

### Project CLAUDE.md Addition

A comprehensive CLAUDE.md snippet is available at **[templates/project-claude-addition.md](../templates/project-claude-addition.md)**. It includes strong information barrier language, an agent quick reference table, directory structure, and usage commands.

The `dark-factory init` command automatically appends this to your project's CLAUDE.md. To add it manually:

```bash
cat dark-factory/templates/project-claude-addition.md >> CLAUDE.md
```

Replace `__SOURCE_DIR__` in the appended content with your actual source directory (e.g., `src`).

### .gitignore Additions

```gitignore
# Dark Factory runtime artifacts (optional — you may want to commit these)
# .dark-factory/reports/
```

Note: DO commit specs, scenarios, and reviews. They're valuable documentation.

### Docker Setup for Teams

All team members need Docker installed. Build images once and share via a registry, or let each developer build locally:

```bash
# Build on each developer machine (recommended for simplicity)
bash docker/build-images.sh node

# Or push to a shared registry
docker tag dark-factory-node registry.example.com/dark-factory-node:latest
docker push registry.example.com/dark-factory-node:latest
```

## Meeting Cadence

### Weekly: Pipeline Retrospective (15 min)
- Review metrics: first-pass rate, avg iterations, escalation rate
- Identify common spec issues
- Refine agent definitions based on results
- Share tips and patterns

### Monthly: Framework Evolution (30 min)
- Review and update agent definitions
- Add new templates for common patterns
- Update tool recommendations
- Address systematic issues

## Collaboration Patterns

### Pair Speccing
Two team members write a spec together. One writes, the other adversarially reviews.
Best for: Complex features, new domains, specs that have failed validation multiple times.

### Spec Review
Before running the Spec Validator, have another team member review the spec.
Best for: Critical features, security-sensitive code, anything customer-facing.

### Pipeline Shadowing
New team member observes an experienced member run the full pipeline.
Best for: Onboarding, building intuition about spec quality.

## Scaling Up

As your team grows beyond 5:

1. **Specialize roles:** Dedicated spec writers, pipeline operators
2. **Build a spec library:** Reusable specs for common patterns (CRUD, auth, etc.)
3. **Automate more:** Full CI/CD pipeline running Dark Factory on every PR
4. **Custom agents:** Tune agent definitions for your specific domain
5. **Metrics dashboard:** Track pipeline health across the team
